# 客户调研

桌面版与 Docker 网页共用客户调研服务；Android 安装版绑定中枢后可查看、启动、停止、清除调研记录，处理重复客户（生成新版本/覆盖旧报告）并手动入库，也能修改流程模板，由中枢执行 Agent 并保存报告，原始资料按同步分类设置同步到手机。主导航打开「客户调研」，输入客户全名或简称，选择「知识库 + 联网调研」或「仅知识库资料」，点击「调研并保存」。需先在桌面端或中枢的「设置 → Agent 与自动化」配置内置 Agent。

报告按 v3 契约生成——在「**先核验客户主体 → 再按证据量选报告模式 → 只写能指回来源的结论**」之上，增加了三条记录与入库纪律：

- **自动入库策略**：内置「调研并保存」的完整报告自动入库；资料不足简报只在客户洞察页反馈，需要时手动入库；主体核验永不入库。
- **重复客户先选处理方式**：知识库里已有该客户的调研报告时，保存前必须由用户选择「生成新版本」还是「覆盖旧报告」，服务端没有拿到选择会拒收。
- **记录可清除**：调研记录能一键/按客户/按记录清除，只删记录、不动知识库里的报告文档；删除以墓碑形式跨端同步。

公开工商与知识库都确认不了主体时，只出「主体核验」短报告并明确质疑客户是否存在、名称是否写错，不写客户分析、不保存文件。

## 多端同步

设置 → 多端同步 → 同步内容 里的「客户洞察多端同步」默认开启。同步的是**调研记录本身**（客户、报告正文、生成日期、流程版本、主体核验结论与已保存的原始资料路径）和**流程与模板**（流程正文 + 8 个固定章节标题）：同步群组内任意一端发起的调研，其余端在客户洞察页都能按客户看到；在任一端改的流程模板，其余端下一次调研即生效，已开始的任务仍保留自己的规则快照。

- **只同步完成态**：已生成报告（含未保存的草稿报告）才跨端；进行中、排队或失败的记录留在执行端，不会在别的设备上显示成一条永远转圈的「进行中」。报告正文与主体核验结论随记录同步，因此即使关闭「原始资料」分类，对端也能在客户洞察里翻阅报告、看到「主体未核实」等警示；已保存的报告文件本身仍走原始资料同步。
- **清除记录有墓碑**：用户清除的记录不直接消失，而是置 `deleted=1`（报告正文、保存路径、核验结论一并清空）并作为**墓碑**同步；对端收到墓碑后也删除该记录，否则对端留着的旧副本会在全量对账时把已删记录「复活」回来。同一时刻的删除与写入冲突按「删除优先」收敛，两端最终看到一致结果。墓碑只删调研记录，知识库里的报告文件仍按「原始资料」分类单独同步，不会随墓碑删除。
- **冲突**：同一任务按记录更新时间「最新者胜」；流程模板按最近一次保存时间取值（与设置类内容相同口径）。
- **Android**：手机端不落调研记录副本，读写都经窄代理直接访问已绑定的中枢（与手机会话、任务看板同一方式），所以手机看到的始终是中枢最新数据；未绑定中枢时无法离线查看客户洞察。

## 流程与报告

### 第一步：核验客户主体

先核对输入名称对应的主体是否存在，再决定写什么；核验结论随报告一起提交（提交契约里的 `identity`）：

- **verified（已核实）**：在公开工商登记或官方渠道找到该主体。尽量拿到工商全名填 `fullName`（保存命名与报告抬头都用它），能拿到统一社会信用代码就填 `registrationId`；`evidence` 指向 kind=registry（企查查/天眼查/国家企业信用信息公示系统等）或 kind=official（官网/年报/公告等）的外部来源。仅「知识库 + 联网调研」范围可声明 verified。
- **kb-docs（仅库内资料）**：外部没核实到，但知识库里确有该客户的实质原始资料（拜访纪要、合同、报价、往来记录）。`evidence` 至少 1 条必须是 `原始资料/` 下的原始文档；只有 Wiki 页面、客户名单或名称提法不算主体证据，不能据此补全客户分析。
- **not-found（查无此主体）**：公开渠道与知识库都确认不了主体。必须列出至少 2 次检索尝试（不同渠道或关键词），`evidence` 留空并写清判定原因（`note`），只提交「主体核验」短报告；报告会明确说未能核实该客户是否存在、名称是否写错或只是品牌简称，不写任何客户分析。客户洞察页会在报告前亮出「查无此主体」警示、判定原因与检索记录，并按当前客户名提供重新发起调研的入口。

「仅知识库资料」范围不能声明 verified；「知识库 + 联网调研」但公开资料不足时按 kb-docs 或 verified+简报处理，不硬凑完整版。

### 第二步：按证据量选报告模式

服务端按 `identity.status` 与提交的章节集合推断模式，不靠模型自觉：

| 模式 | 适用 | 章节（每章正文上限，字） |
| --- | --- | --- |
| 完整报告 | 仅「知识库 + 联网调研」且 verified；来源 ≥3 条、外部来源 ≥2 条、其中至少 1 条工商/官方来源，「已核实事实」≥2 处引用、「需求与机会」≥1 处引用 | 结论 400 / 客户主体与核实 900 / 已核实事实 1200 / 需求与机会 1200 / 决策链与关系 900 / 风险与反证 700 / 下一步行动 1000 / 待核实 700 |
| 资料不足简报 | 「仅知识库资料」、kb-docs，或已核实主体但公开资料不够写完整版 | 结论 350 / 已知事实 800 / 待核实 500（「已知事实」至少 1 处引用） |
| 主体核验 | not-found：公开工商与知识库都确认不了主体 | 核验结论 300 / 需要你确认 300；「核验过程」由服务端按检索尝试生成 |

完整版达不到来源或引用门槛会被拒收并提示改交简报；简报与主体核验的章节标题固定，完整版的 8 个章节标题可在「流程与模板」里改。

### 第三步：只写有依据的结论

- 结论先行；只写与该客户直接相关、能指回来源的事实，正文用 `[来源编号]` 引用；超出长度上限或引用不存在的来源会被拒收。
- 推断标「推断」，不确定写「待核实」；没有的写没有，不用「行业趋势 / 市场空间 / 国产替代」这类通用叙述填充。
- 禁止方法论、能力声明、检索过程与免责声明等元叙述（范围与来源统计由服务端页头生成），也禁止「本章主要…」「综上所述」「随着…发展」「具有重要意义」这类版面话术与空话。
- 正文不要再写 `#`/`##` 标题，标题由模板生成。

### 保存与命名

- 完整报告存 `原始资料/文档/YYYY.MM.DD_<工商全名>调研报告.md`；资料不足简报存 `原始资料/文档/YYYY.MM.DD_<工商全名或客户名>调研简报.md`；主体核验只留调研记录，不保存文件；什么时候真正落盘见「自动入库策略」。
- 日期取任务开始时用户时区的自然日；生成新版本时重名依次追加 `_2`、`_3`（例如 `2026.01.01_某某有限公司调研报告_2.md`），已有文件及回收站中的同名报告均不覆盖；用户选择「覆盖旧报告」时改为整篇替换同一份文件（见「重复客户：生成新版本 / 覆盖旧报告」）。
- 一份任务只对应一份完成态报告：重复提交同一份内容返回已保存路径，改动内容会报「已保存报告不可覆盖」，需要新一轮请重新发起调研。保存失败不标成功。
- 客户洞察页任务状态：`报告已保存` / `报告未入库`（完整报告未保存）/ `简报未入库`（资料不足简报未保存）/ `主体未核实`（主体核验报告）；执行中、失败、停止等状态沿用 Agent 会话状态。未入库记录在客户档案头有「存入知识库」按钮（主体核验没有入库入口）。

### 流程与模板

「流程与模板」可修改流程正文和 8 个章节标题。内置与外部 Agent 每次开始任务都读取同一版本，已开始的任务保留自己的规则快照；完整版按快照里的标题渲染，简报/主体核验用固定标题。章节标题不能重复，也不能用「来源与结论对照」（该章由系统固定生成）。

**旧模板升级**：模板带契约版本标记（当前 `contract=3`）。v1 的八章 ACS 模板没有标记、v2 模板标记为 2，服务端读到与当前契约不一致的模板时会按当前默认模板（流程正文 + 8 个章节）重建并把模板版本 +1；用户在旧模板里自定义的流程正文与章节标题会一并重置，需要重新填写。历史报告的「流程版本」仍按任务快照显示。

## 重复客户：生成新版本 / 覆盖旧报告

发起保存型调研前，服务端会先在知识库 `原始资料/文档/` 里查该客户已有的调研报告（`POST /api/customer-research/existing`；`engram research begin` 的返回里也带 `existingReports`）。识别按报告文件名里的客户名做**全名/简称互相包含**匹配（忽略空格、括号与大小写），兼容 v1 的 `YYYY.MM.DD_<客户>_客户调研_xxx.md` 命名；只看知识库文档，**删调研记录不影响命中**，回收站里的报告不算。每条返回 `path` / `title` / `customerName` / `reportDate` / `kind`（完整报告或简报）/ `updatedAt`，最近更新在前。

界面在发起调研时先查已有报告：有就弹出「知识库里已有该客户的报告」选择框，默认选中最近更新的一份，可以「生成新版本（保留旧报告）」或「覆盖选中的报告」；覆盖前明确提示旧文档内容不再保留。

契约（内置与外部 Agent 共用）：

- `save=true`（或内置「调研并保存」）且 `existingReports` 非空时，**必须**带 `saveMode`：
  - `saveMode=new`：生成新版本，文件名按本次日期与客户名重新生成，重名追加 `_2`、`_3`，旧报告原样保留。
  - `saveMode=overwrite` + `overwritePath`（取 `existingReports[].path`，不在列表里的路径会被拒）：**整篇替换同一份文件**——文件名与日期保持不变、不新增文件，正文整段替换、frontmatter 更新时间，响应 `overwritten=true`。
- 没带 `saveMode` 时服务端直接拒收并提示先与用户确认「生成新版本还是覆盖旧报告」；外部 Agent 必须先问用户，不能自己替用户选。
- 覆盖是破坏性动作：只在用户明确选择时执行；覆盖后同一份内容重复提交幂等，已入库报告不能再改内容——要更新请重新发起调研并再次选择覆盖。
- **目标丢失退回新版本**：发起后、入库前覆盖目标被删除、改名或移入回收站时，服务端自动退回生成新版本（`overwritten=false`，本次报告仍会写入），避免调研成果丢失。
- 任务行记下 `saveMode` / `overwritePath`；资料不足简报是手动入库，用户在页面点「存入知识库」时才真正覆盖或新建，同样遵守上面的选择。

## 自动入库策略

| 场景 | 是否入库 | 说明 |
| --- | --- | --- |
| 内置「调研并保存」+ 完整报告 | 自动入库 | 任务状态「报告已保存」，客户档案有「打开原始资料」入口 |
| 内置「调研并保存」+ 资料不足简报 | 不自动入库 | `saved=false`、`path` 为空，任务状态「简报未入库」；只在客户洞察页反馈，可点「存入知识库」手动入库 |
| 外部 Agent + `save=true`（完整报告或简报） | 入库 | 必须由用户明确要求保存；简报在显式保存时也可入库 |
| 外部 Agent 未传 `save` | 不入库 | 只出报告预览，仍可在客户洞察页翻阅 |
| 主体核验（not-found） | 永不入库 | 没有可核实主体，页面没有入库入口，调用手动入库接口会被拒 |

- 手动入库（`POST /api/customer-research/save {taskId}`）返回 `{saved, path, overwritten}`：未入库简报生成 `…调研简报.md`，未入库完整报告生成 `…调研报告.md`；已入库再点一次返回原路径，不重复建文件。
- 未生成报告的记录、主体核验记录拒绝入库（分别提示「还没有生成报告」「主体未核实」）。
- 资料不足简报「不自动入库」是为了不让证据不足的内容悄悄变成知识库来源；用户判断有参考价值时再手动入库。

## 记录管理

调研记录在客户洞察页按客户汇总，可单独删除某条、清掉某个客户的全部记录或一键清空：

- **一键清除**（页头）清掉全部调研记录；**清除记录**（客户档案头）只清当前客户；**删除**（右栏「调研记录」每条）只清这一条。
- 对应接口 `POST /api/customer-research/delete`，body 三选一：`{taskIds:[…]}` / `{customer:"…"}` / `{all:true}`，返回 `{deleted: 数量}`。
- **只删记录，不动知识库文档**：清除把记录置为软删除墓碑（`deleted=1`，报告正文、保存路径、核验结论一并清空），`原始资料/文档/` 里已入库的报告文件与页面保持原样；已清除记录不能再提交报告或手动入库（提示「这条调研记录已被清除，请重新发起调研」）。
- **进行中拒绝**：记录关联的执行轮次处于 `running`/`queued` 时拒绝清除（提示先停止），避免用户以为调研被停掉而实际还在跑；停止后再清。
- **多端同步墓碑**：墓碑随「客户洞察多端同步」跨端，对端收到后同样删除该记录；同刻的删除/写入按「删除优先」收敛。知识库报告文件按「原始资料」分类单独同步，不随墓碑删除（见「多端同步」）。
- **Android**：手机端不落记录副本，三条新操作都由本地窄代理转发到中枢——`POST /api/customer-research/existing`（查已有报告）、`POST /api/customer-research/delete`（清除记录）、`POST /api/customer-research/save`（手动入库）；报告文件的增删只在执行端（中枢）发生。

## 外部 Agent

外部 Agent 必须是**能跑 shell 的客户端**（Claude Code / Codex / DeepSeek Harness / ZCode / Kimi Code CLI / WorkBuddy / Qoder），交互统一走 `engram` CLI + skill：服务端不再提供 MCP 端点，也没有 `mcp__engram__*` 工具。

统一命令 `engram research begin --customer <客户> [--scope knowledge-web|knowledge-only] [--save] [--save-mode new|overwrite] [--overwrite-path <path>] [--client <客户端>] [--timezone <时区>]`：返回任务 ID、流程正文、模板版本、`identityContract`（主体核验要求）、`reportContract`（三种模式的章节、每章上限、来源格式）、`modeRules`（何时用哪种模式），以及 `existingReports`（知识库里该客户已有报告）与 `saveMode`（本次的保存方式，未选为空串）；`engram research submit` 校验通过后才算完成。客户端入口 skill 只说明何时使用与如何调用，契约以服务端返回为准，不在客户端复制一份。

`engram research submit --task <taskId> --file report.json`（报告 JSON 字段 `identity` / `sections` / `sources` / `save` / `saveMode` / `overwritePath`）：

- **identity 必填**（v1 的 `companyFullName` 会被明确拒绝）：`status`=verified / kb-docs / not-found，`method`=registry / official-site / kb-documents / none，`attempts` 1–12 条检索记录，`evidence` 指向 sources 里的来源编号；verified 还要 `fullName`（可带 `registrationId`）。
- **模式由 status + 章节集合推断**：not-found 只接受 `summary`/`gaps` 两章；完整报告除 8 章外还要满足上面的来源与引用门槛；其余为三章简报。模式不符会返回明确的修正提示，按提示改交对应模式，不要绕过校验改用 `engram files add`。
- **sources** 每条 `{id, title, url 或 path（只能二选一）, kind: registry|official|media|kb-doc|kb-page, publishedAt, accessedAt}`；「仅知识库资料」不能带 url；kb-docs 证据必须含 `原始资料/` 下的原始文档且不得掺外部网页；verified 仅限「知识库 + 联网调研」。
- **保存语义**：内置「调研并保存」按钮已授权保存——完整报告自动入库，资料不足简报只留页面反馈、不自动入库（不要声称已保存），主体核验不落文件；外部对话只有在用户明确要求保存时才传 `--save`（显式保存时简报也可入库），其余默认只出报告预览（可在客户洞察翻阅）。not-found 永不保存文件。结构校验不证明事实真伪，网页来源仍需 Agent 实际阅读核查。
- **保存方式**：`--save`（或报告 JSON 里的 `save=true`）且 `existingReports` 非空时，必须带 `--save-mode new` 或 `--save-mode overwrite --overwrite-path`（取 `existingReports[].path`）；不先问用户就直接提交会被拒收。详见「重复客户：生成新版本 / 覆盖旧报告」与「自动入库策略」。

在「设置 → Agent 与自动化 → 外部接入」一键接入（只装 CLI 包装脚本 + skill，**不再改客户端的 MCP 配置**）：
